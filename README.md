# Concertina and HCTR2 on the nRF52840 and nRF52832 (Cortex-M4F)

Port of the Concertina reference implementation (AArch64, ARMv8 Crypto
Extension) to the Nordic nRF52840 and nRF52832, with HCTR2 and AES-XTS
measured under the
same conditions as in the AArch64 benchmark: one AES implementation shared by
all modes, AES-128, a 16-byte tweak, message lengths 32 to 4096 bytes, best of
15 runs. Bare-metal firmware: self-tests, a usage example and the benchmark,
printed on the UART. The specification, the byte encoding and the known
answers of Concertina are those of the original repository
(`src/kat_generated.h`, from `python/scheme_ref.py`); HCTR2 is validated
against the official vectors of https://github.com/google/hctr2.

Companion code for the paper *Concertina: A Birthday-Bound Secure Tweakable
Variable-Length Wide-Block Mode* by Gülnihal Öztürk, Onur Koçak and Oğuz
Yayla.

`paper/appendix_mcu.tex` is the paper's appendix on the microcontroller
implementations, covering **both chips** (tables included), generated by
`tools/make_tables.py` from
`paper/appendix_mcu.in.tex` and the results in `results/<chip>/`; every
number in its text is filled in from the data (`results/values.txt`), and the
statements it makes are checked by the script (`results/summary.txt`).
Bibliography entries added for the appendix: `paper/mcu_refs.bib`.

## Quick start

```sh
sudo apt-get install gcc-arm-none-eabi libnewlib-arm-none-eabi   # GCC 13.2 (Ubuntu 24.04)
pip install -r requirements.txt
make host                                   # portable code, natively
python3 emu/test_cryptocell.py              # CryptoCell model
make CHIP=nrf52840 emu                      # firmware in the emulator: self-tests + benchmark
make CHIP=nrf52832 emu
```

No toolchain? `python3 emu/nrf52_emu.py --chip <chip> prebuilt/<chip>/concertina.elf`
runs the published images. The CI workflow (`.github/workflows/ci.yml`) runs
the host tests, the model tests and every firmware self-test of both chips in
the emulator.

## The two chips, and what each mode runs on

| | nRF52840 | nRF52832 (QFAA) |
|---|---|---|
| core | Cortex-M4F, 64 MHz; no AES/SHA/carry-less multiply instructions | same |
| flash / RAM | 1 MiB / 256 KiB | 512 KiB / 64 KiB |
| AES hardware | **CryptoCell-310**: AES-128 encryption **and decryption** (DMA); ECB peripheral (encryption) | **ECB peripheral only**: AES-128, encryption of single blocks |
| hash hardware | **CryptoCell-310: SHA-256** (also SHA-1/224) | none |
| carry-less multiply | none (the CryptoCell has no GHASH) | none |
| **Concertina** | AES and the SHA-256 compression on the CryptoCell (HMAC with precomputed ipad/opad states, padding in software); HMAC-SHA3-256: Keccak in software | AES on the ECB peripheral; HMAC-SHA-256 / HMAC-SHA3-256 in software |
| **HCTR2** | AES (both directions) on the CryptoCell; POLYVAL in software (ct32, 4-bit table, 8-bit table) | forward AES on ECB; POLYVAL in software (3 variants); the one inverse-cipher block of decryption in software (table, or constant-time bitsliced from BearSSL) |
| **AES-XTS** (reference) | CryptoCell, both directions | ECB for encryption and tweaks; inverse cipher in software (table) |
| t_ECB (PS) | 7.2 µs maximum (461 cycles) | 6 µs typical (384 cycles) |
| UARTE TXD.MAXCNT | 16 bits | 8 bits |
| DK, console / LEDs | nRF52840 DK: P0.06 / P0.13–16 | nRF52 DK: P0.06 / P0.17–20 |

Neither Concertina's counter `E(S xor <i>)` nor HCTR2's XCTR counter
`E(S xor le64(i))` is the CryptoCell's CTR mode, so both modes prepare counter
blocks on the CPU and encrypt them 16 per DMA transfer (same code for both).
The CryptoCell is initialised on first use (images that do not use it do not
contain the driver). Software-only configurations of every mode are also
measured; their numbers are identical on both chips.

## Implementations

| Component | AArch64 original | nRF52840 port |
|---|---|---|
| AES (all modes) | AESE/AESMC | 32-bit table code, one 1 KiB table built in RAM at start-up (no data cache on either chip); AES-128/192/256 |
| AES inverse (HCTR2, XTS only) | AESD/AESIMC | second 1 KiB table, inverse S-box, equivalent inverse key schedule (`src/aes_dec.c`); not linked into Concertina |
| AES-128 (hardware) | – | **ECB peripheral** (`AES_IMPL_ECB`, forward only, both chips); **CryptoCell-310** (`AES_IMPL_CC310`, both directions, nRF52840, `board/cc310_nrf52840.c`) |
| AES inverse, constant-time | – | BearSSL `aes_ct` bitsliced (`src/aes_ct.c`, `AES_IMPL_CT`) |
| Keccak-f[1600] | SHA-3 instructions | **bit-interleaved 32-bit** (generated by `tools/gen_keccak_bi32.py`); the 64-bit code of the original as reference backend |
| SHA-256 | SHA-2 instructions | portable code of the original, rounds unrolled by eight; the unchanged code as reference backend; **CryptoCell** compression function (`SHA256_IMPL_CC310`) |
| POLYVAL | PMULL / portable ctmul64 | **ct32**: 32x32->64 multiplications (UMULL, single cycle on Cortex-M4) on bit-masked operands, Karatsuba, Montgomery reduction by shifts; **ct64**: the portable code of the original, unchanged; **table4** / **table8**: Shoup's method with 4-bit (256 B/key, as in mbed TLS) and 8-bit (4 KiB/key) tables, via the RFC 8452 relation to GHASH (`tools/gen_ghash_tables.py`) |
| HCTR2, XCTR, AES-XTS | NEON types | plain C on the shared AES |
| Timing | wall clock | `DWT->CYCCNT` |

APIs: `src/scheme.h` (Concertina), `src/hctr2.h`, `src/xts.h`.

```c
scheme_ctx c;
scheme_setkey(&c, key, 16, SCHEME_HMAC_SHA256, SHA256_IMPL_CC310, AES_IMPL_CC310);
scheme_encrypt(&c, ct, pt, len, tweak);   /* len >= 32, 16-byte tweak, in place allowed */

hctr2_ctx h;
hctr2_setkey(&h, key, 16, POLYVAL_IMPL_CT32, AES_IMPL_ECB, AES_IMPL_CT); /* POLYVAL, AES, AES^-1 */
hctr2_crypt(&h, ct, pt, len, tweak, 16, 1);   /* 1 = encrypt, 0 = decrypt */
```

Build options used for the memory measurements: `AES_MAX_NR=10` (AES-128
round keys only), `AES_ECB_ONLY=1` (forward AES on the ECB peripheral only),
`AES_CC310_ONLY=1` (AES on the CryptoCell only), `AES_DEC_TABLE`,
`AES_DEC_CT`, `AES_WITH_ECB`, `AES_WITH_CC310`, `KECCAK_WITH_REF64`,
`SHA256_WITH_SW/REF/CC310`, `POLYVAL_WITH_CT32/CT64/TABLE4/TABLE8`,
`SCHEME_WITH_SHA3/SHA256` (see `tools/footprint.py`).

## Self-tests

Run on the target before the benchmark, for **every backend available on the
chip** (software, ECB, CryptoCell): AES and AES^-1 (FIPS 197, round trips),
ECB and CryptoCell against software, SHA3-256 / Keccak-f and SHA-256 (all
backends, CryptoCell against software on random inputs), 90 HMAC and 90
Concertina known answers, POLYVAL (96 vectors, four implementations), XCTR
(180) and HCTR2 (700) official vectors for every POLYVAL / AES / AES^-1
combination, encryption and decryption, and 14 AES-XTS known answers:
13 427 checks on the nRF52840, 11 604 on the nRF52832 (24 272 / 20 280 with
`SELFTEST_FULL_SPLITS=1`, every HMAC split point).

## Build and run on a board

Requirements: `arm-none-eabi-gcc` (tested with 13.2), `make`, `nrfjprog` (or
any J-Link/CMSIS-DAP tool).

```sh
make                    # nRF52840: build/nrf52840/concertina.{elf,hex,bin}
make CHIP=nrf52832      # nRF52832: build/nrf52832/...
make flash [CHIP=...]   # DK: nrfjprog --program ... --chiperase --verify --reset
```

Or flash `prebuilt/<chip>/concertina.hex` (the images are chip-specific:
memory size, LED pins). Open the DK's J-Link virtual COM port at
**115200 8N1**. LED1 is on while the tests run, then LED2 (pass) or LED4
(fail). The benchmark prints tables in **DWT cycles** and `CSV,` lines; save
the UART log. (On a board the cycle counts are real; the appendix would
then use them instead of the estimates, see the TODO at its top.)

* Other boards: `make UART_TX_PIN=<n>` (nRF52840: P1 pins are 32 + n). Linked
  at 0x0 for a chip without SoftDevice or bootloader; otherwise move
  `FLASH ORIGIN` in `board/<chip>.ld`.
* nRF52832: the nRF52832-QFAB (256 KiB flash / 32 KiB RAM) is too small for
  the benchmark firmware with all test vectors.
* If the debugger cannot connect after flashing a revision 3 chip, run
  `nrfjprog --recover` (APPROTECT).

## Emulator and results

```sh
pip install -r requirements.txt
make results CHIP=nrf52840 && make results CHIP=nrf52832   # results/<chip>/, ~10 min
make paper                                                  # paper/appendix_mcu.tex
```

`emu/nrf52_emu.py --chip <chip>` runs the **same ELF** in Unicorn (QEMU's ARM
core, Cortex-M4 model) with the memory map of the chip and models of CLOCK,
UARTE0 (EasyDMA, MAXCNT width of the chip), ECB, GPIO, DWT and, on the
nRF52840, the **CryptoCell-310** (`emu/cryptocell.py`): AES-128 ECB
encryption/decryption and the SHA-256 compression over its DMA interface.
Register addresses and reset values come from Nordic's SVD; the semantics the
SVD leaves open (key word order, `HASH_H[i]` = H_i, padding configuration)
follow Arm's own CryptoCell drivers (CC312 runtime and TF-M v2.0.0 cc3xx,
same register layout). The model rejects what the documentation forbids
(access while disabled, clocks off, DMA outside SRAM, transfers over
2^16 − 1 bytes, key/state registers written out of order, unmodelled
modes). Results are computed independently of the firmware (`cryptography`;
a FIPS 180-4 compression checked against `hashlib`). `emu/test_cryptocell.py` tests the model on its own
(known answers and each rejected case; run by `make results`).

### What is exact and what is estimated

* **Exact** (a board running the same image gives the same values): flash
  size, static RAM, context size, peak stack (stack painting), executed
  instructions (apart from busy-wait iterations, which the emulator leaves
  after one test), and the number and size of hardware operations per
  message (ECB blocks; CryptoCell AES/SHA-256 transfers and blocks; for data
  in RAM — flash-resident input goes through a 256-byte bounce buffer).
* **Against the models only**: correctness of the hardware backends. All
  test vectors pass in the emulator, but the CryptoCell driver has not run on
  silicon; the HASH_H word order and the HASH_ENDIANNESS meaning (the SVD's
  description contradicts its reset value) come from Arm's CC-312 drivers.
  The firmware's self-tests would catch a mismatch on a board.
* **Estimated**: time. CPU part: executed instructions converted to cycles
  with the Cortex-M4 TRM timings (`emu/m4_timing.py`; taken-branch refill
  P = 1..3; no flash wait states). Hardware part: a latency per operation —
  ECB: t_ECB from the PS (6 µs typical on the nRF52832); CryptoCell: three
  profiles (`CC_PROFILES` in `emu/nrf52_emu.py`), cycles at 64 MHz:

  | | fast | central | slow |
  |---|---:|---:|---:|
  | per DMA transfer | 16 | 64 | 256 |
  | per AES-128 block | 40 (4 cycles/round, AES_HW_FLAGS in the PS) | 56 (wolfSSL: 17.3 MiB/s AES-CBC on an nRF52840 DK) | 112 |
  | per SHA-256 block | 64 (1 round/cycle, assumed) | 151 (wolfSSL: 25.9 MiB/s) | 302 |

  Every time is linear in these latencies and the CPU part does not depend
  on them, so `make results` also runs the benchmark with each latency set to
  zero; `tools/make_tables.py` recovers the operation counts per line, checks
  the split against the fast and slow runs, and gives the results under all
  combinations (P × profile) and the break-even latencies.

On the nRF52840, Concertina (HMAC-SHA-256) is faster than every HCTR2
variant from 256 bytes on under **all** P × profile combinations (at 4096 B:
2.86–5.94× vs 8-bit tables, 4.68–10.38× vs ct32); HCTR2 is faster at 32 bytes.
For HCTR2 to match it at 4096 bytes, POLYVAL would have to cost under ~55
cycles per block (≤ 98 under any assumption), against 476 for the 8-bit
tables. With HMAC-SHA3-256 (no SHA-3 hardware) Concertina is slower than
HCTR2 on both chips. On the nRF52832 (no hash hardware), Concertina never
beats HCTR2 with 8-bit tables; it beats a fully constant-time HCTR2 from
1024 B (encryption) / 256 B (decryption). HCTR2 decryption with the
constant-time inverse cipher costs 8,131 cycles more per message than with
tables. All statements made in the appendix are checked by `make paper`
(`results/summary.txt`, "claim ok" lines).

`tools/footprint.py --chip <chip>` builds each configuration alone
(`board/footprint_main.c`) and measures flash, static RAM, context and peak
stack; the linker scripts place newlib's 64-byte-aligned `strlen` first, so
that flash sizes do not depend on alignment padding. Basic-block boundaries
depend on code placement, which changes the cycle estimates by up to 0.2%
between builds; instruction counts do not change.
